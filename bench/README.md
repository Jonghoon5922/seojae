# 측정

같은 질문을 매번 던져서 **값이 바뀌면 알아채는 것**이 목적이다.

```bash
python bench/measure.py testdata\seojae
```

- 시나리오: `scenarios.yaml` — **네가 실제로 물어볼 말**을 적어라
- 결과: `results/최근.md` (사람이 읽는 것), `results/<시각>.json` (기계가 읽는 것)
- 기대와 어긋나면 종료 코드 1

`results/최근.md` 만 git에 넣는다. `git log -p bench/results/최근.md` 로
숫자가 어떻게 움직였는지 볼 수 있다. 시각별 JSON은 안 넣는다 — 매 실행마다
파일이 하나씩 늘면 히스토리가 지저분해진다.

## 무엇을 재나

**이 코드는 LLM을 부르지 않는다.** 그래서 "Claude가 실제로 쓴 토큰"은 못 잰다.
대신 **Claude 앞에 놓이는 글자 수**를 잰다. 답을 만들려면 그만큼은 읽어야 하므로
토큰의 하한이자 가장 정직한 대리 지표다.

| | |
|---|---|
| 서재 전체를 읽는다면 | 상한선. 검색이 아예 없을 때 |
| 답이 든 파일만 읽는다면 | 비교 기준 |
| 검색 결과만 읽는다면 | 하한선 |

**비교 기준은 서재 없는 쪽에 유리하게 잡았다.** 어느 파일을 열어야 하는지 이미
안다고 가정하기 때문이다. 실제로는 그 파일을 찾는 비용이 더 든다. 그러니 여기
나오는 배수는 실제보다 **작다**.

## 두 극단 사이 어디쯤인가

**문서를 펼치면(`get_document`) 절감은 사라진다.** 검색 결과를 읽고 그 문서를
통째로 다시 읽으면 오히려 검색한 만큼 더 든다.

그래서 실제 절감은 **Claude가 얼마나 자주 펼치느냐**에 달렸고, 그 비율은
대출 기록(`readings`)에 남는다. 측정 결과의 "검색 N회에 펼침 M회"가 그것이다.
기록이 쌓일수록 이 숫자가 믿을 만해진다.

## 평균에서 빼는 것

| 빼는 것 | 왜 |
|---|---|
| 헛걸음 (`hint` 가 뜬 질문) | 틀린 답을 싸게 얻은 것은 절감이 아니다 |
| 알려진 구멍 (`known_gap`) | 결과가 그럴듯할 뿐 답이 아니다 |

## 색인 비용 (실측, 578문서 · 19,648청크)

| | |
|---|---|
| 처음 색인 | **106.3초** — 한 번만 |
| 변경 없이 다시 | 1.2초 |
| 1건 추가 | 1.2초 |

한 번 106초를 내고 그 뒤로는 사실상 공짜다. **그래서 오래 살고 여러 번 참조되는
문서가 서재감이다.** 한 번 쓰고 마는 문서는 꽂는 수고가 낭비다.

## 시나리오 쓰는 법

```yaml
- ask: 예외 처리 규약
  why: 왜 이걸 재는지. 나중의 내가 읽는다
  expect:
    min_hits: 3          # 이만큼은 나와야 한다
    hint: false          # 힌트가 뜨면 오탐이다
    sources: [규정.md]    # 이 파일이 결과에 있어야 한다
```

답할 수 없는 질문인데 결과는 그럴듯하게 나오는 경우는 `expect` 대신 `known_gap` 에
이유를 적는다. 실패로 세지 않되 매번 눈에 띄게 남는다.
